In a multi-user B2B dashboard, showing the wrong data to the wrong person isn't just a UX problem — it's a security, compliance, and in some cases legal problem. A junior analyst who sees gross margin by internal competitor, a salesperson who accesses other salespeople's commissions, a user from one branch who sees another branch's data — all real scenarios that happen when RBAC is implemented superficially.

Correct RBAC implementation in dashboards requires four layers working together: the permissions model, route protection, UI component hiding, and — most importantly — data filtering in the backend.

## Permissions Model: Roles, Permissions, and Resources

The most common mistake in beginner RBAC is confusing roles with permissions. A role is a grouping (admin, manager, analyst, operator). A permission is an atomic capability (read_financial_report, export_data, edit_settings). A resource is the object the permission applies to (report, dashboard, user).

The most robust structure for B2B dashboards uses all three levels:

```typescript
// types/rbac.ts
export type Action = 'read' | 'write' | 'delete' | 'export';
export type Resource =
  | 'dashboard:financial'
  | 'dashboard:operations'
  | 'dashboard:hr'
  | 'reports:revenue'
  | 'reports:customers'
  | 'users:management'
  | 'settings:billing';

export type Permission = `${Action}:${Resource}`;

export type Role = 'super_admin' | 'admin' | 'manager' | 'analyst' | 'viewer';

export const ROLE_PERMISSIONS: Record<Role, Permission[]> = {
  super_admin: ['read:dashboard:financial', 'write:dashboard:financial', 'export:reports:revenue', /* ... all */],
  admin: ['read:dashboard:financial', 'read:dashboard:operations', 'export:reports:revenue', 'write:users:management'],
  manager: ['read:dashboard:financial', 'read:dashboard:operations', 'read:reports:revenue', 'read:reports:customers'],
  analyst: ['read:dashboard:operations', 'read:reports:customers', 'export:reports:customers'],
  viewer: ['read:dashboard:operations'],
};

export function hasPermission(role: Role, permission: Permission): boolean {
  return ROLE_PERMISSIONS[role]?.includes(permission) ?? false;
}
```

This model is easily extensible. When a client asks "I want the regional manager to see only their region's metrics but not be able to export," you create a `regional_manager` role with specific permissions without touching the existing logic.

Store roles in the JWT or session, but **never trust only the client to determine permissions**. The JWT can carry the role to avoid a DB query on every request, but the backend needs to validate independently.

## Route Protection in Next.js with Middleware

In Next.js App Router, edge middleware is the right place for route protection — it runs before any page is rendered, without needing to load the full application bundle.

```typescript
// middleware.ts
import { NextRequest, NextResponse } from 'next/server';
import { jwtVerify } from 'jose';

const ROUTE_PERMISSIONS: Record<string, string> = {
  '/dashboard/financial': 'read:dashboard:financial',
  '/dashboard/hr': 'read:dashboard:hr',
  '/reports/revenue': 'read:reports:revenue',
  '/settings/billing': 'read:settings:billing',
};

export async function middleware(request: NextRequest) {
  const token = request.cookies.get('session')?.value;

  if (!token) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  try {
    const { payload } = await jwtVerify(
      token,
      new TextEncoder().encode(process.env.JWT_SECRET!)
    );

    const userRole = payload.role as string;
    const path = request.nextUrl.pathname;

    // Check if the route requires a specific permission
    const requiredPermission = Object.entries(ROUTE_PERMISSIONS).find(
      ([route]) => path.startsWith(route)
    )?.[1];

    if (requiredPermission) {
      const rolePerms = ROLE_PERMISSIONS[userRole as Role] ?? [];
      if (!rolePerms.includes(requiredPermission as Permission)) {
        return NextResponse.redirect(new URL('/unauthorized', request.url));
      }
    }

    return NextResponse.next();
  } catch {
    return NextResponse.redirect(new URL('/login', request.url));
  }
}

export const config = {
  matcher: ['/dashboard/:path*', '/reports/:path*', '/settings/:path*'],
};
```

The middleware protects against direct URL access. An analyst who tries to directly access `/dashboard/financial` will be redirected to `/unauthorized` — they won't see a blank screen, a 500 error, or the data.

## UI Component Hiding by Permission

Route protection is necessary but not sufficient. Within a single screen, different elements may be available to different roles. The "Export to Excel" button, the gross margin card, the "Manage Users" link in the menu — all may need component-level protection.

The recommended approach is a hook and guard component:

```typescript
// hooks/usePermission.ts
import { useSession } from 'next-auth/react';

export function usePermission(permission: Permission): boolean {
  const { data: session } = useSession();
  const role = session?.user?.role as Role | undefined;

  if (!role) return false;
  return hasPermission(role, permission);
}

// components/PermissionGate.tsx
interface PermissionGateProps {
  permission: Permission;
  children: React.ReactNode;
  fallback?: React.ReactNode;
}

export function PermissionGate({ permission, children, fallback = null }: PermissionGateProps) {
  const allowed = usePermission(permission);
  return allowed ? <>{children}</> : <>{fallback}</>;
}

// Usage in any component:
<PermissionGate permission="export:reports:revenue">
  <ExportButton />
</PermissionGate>

<PermissionGate
  permission="read:dashboard:financial"
  fallback={<LockedMetricCard message="Access restricted" />}
>
  <RevenueMetricCard />
</PermissionGate>
```

The `fallback` component matters: simply hiding elements without explanation can confuse users who know the data exists. An "access restricted" card communicates that the data exists but requires permission, which is more honest than rendering nothing.

## Backend Data Filtering by Role

All the UI protection described above is **comfort security**. It improves the experience and prevents confusion, but it doesn't truly protect data. Real protection lives in the backend.

Any API endpoint or Server Action returning sensitive data must verify the authenticated user's permissions and filter results accordingly:

```typescript
// app/api/reports/revenue/route.ts
import { getServerSession } from 'next-auth';
import { authOptions } from '@/lib/auth';
import { hasPermission } from '@/lib/rbac';
import { db } from '@/lib/db';

export async function GET(request: Request) {
  const session = await getServerSession(authOptions);

  if (!session?.user) {
    return Response.json({ error: 'Unauthenticated' }, { status: 401 });
  }

  const role = session.user.role as Role;

  if (!hasPermission(role, 'read:reports:revenue')) {
    return Response.json({ error: 'Insufficient permission' }, { status: 403 });
  }

  // Managers only see data from their organizational units
  const orgUnitFilter = role === 'manager'
    ? { orgUnitId: session.user.orgUnitId }
    : {};

  const data = await db.revenue.findMany({
    where: orgUnitFilter,
    orderBy: { date: 'desc' },
  });

  return Response.json(data);
}
```

## Conclusion

Well-implemented RBAC in B2B dashboards requires all four layers working together: clear permissions model, edge route protection, UI component guards, and backend data filtering. Implementing only some of these layers creates false senses of security.

The investment in proper RBAC is particularly important in B2B SaaS with multiple customers and multiple roles per customer. Once the permissions system is well-defined at the start of the project, adding new roles and new resources is straightforward.
