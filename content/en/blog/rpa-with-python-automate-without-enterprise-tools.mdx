RPA — Robotic Process Automation — has become synonymous with UiPath, Automation Anywhere, and Blue Prism: enterprise platforms with six-figure annual contracts, implementation teams, and steep learning curves. But the truth is most companies don't need any of that. If a process can be described in logical steps and happens on a computer, Python solves it.

The premise of RPA is simple: automate the repetitive work a human does in front of a computer. Logging into systems, extracting data from spreadsheets, filling out forms, sending rule-based emails, generating reports — all of this can be done by a Python script running in the background, with no license cost, no vendor lock-in, and full control of the code.

In this article you'll see which tools to use for each type of automation and how to structure scripts that don't break on the first layout change.

## Playwright vs Selenium vs PyAutoGUI: When to Use Each

Before writing a line of code, you need to choose the right tool for the type of interaction you want to automate.

**Playwright** is the choice for modern web automation. Developed by Microsoft, it controls real browsers (Chromium, Firefox, WebKit) with an async API and features Selenium never had: auto-wait, network interception, multiple browser contexts, and native screenshots/videos. It's faster to develop with and more stable in production.

**Selenium** still makes sense when you need compatibility with legacy code or when the target system has specific behaviors that only work with older Chrome versions. For new projects, prefer Playwright.

**PyAutoGUI** is different from the other two: it doesn't control the browser, it controls the entire computer. Moves the mouse, clicks on screen positions, types text, presses keys. It's the only option for systems without a web interface — legacy desktop applications, SAP GUI, locally installed ERP systems. The trade-off is that it's fragile: any change in resolution, theme, or window position can break the script.

```
Target system            → Recommended tool
─────────────────────────────────────────────
Website / Web App        → Playwright
Legacy web system        → Selenium (compatibility)
Desktop app / ERP        → PyAutoGUI
PDF / Spreadsheet        → pdfplumber + openpyxl (no RPA)
API available            → requests + httpx (no RPA)
```

Practical rule: if there's an API, use the API. RPA is the last resort, not the first.

## Web Automation: Login, Data Extraction, and Forms

The most common web RPA use case is accessing a portal without an API, logging in, extracting or submitting data, and logging out. With Playwright in Python:

```python
from playwright.sync_api import sync_playwright
import json

def extract_orders_portal(username: str, password: str) -> list[dict]:
    orders = []

    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        page = browser.new_page()

        # Login
        page.goto("https://vendor-portal.example.com/login")
        page.fill("#username", username)
        page.fill("#password", password)
        page.click("button[type='submit']")
        page.wait_for_url("**/dashboard")

        # Navigate to orders
        page.click("nav >> text=Orders")
        page.wait_for_selector("table.orders-table")

        # Extract table rows
        rows = page.query_selector_all("table.orders-table tbody tr")
        for row in rows:
            cols = row.query_selector_all("td")
            orders.append({
                "number": cols[0].inner_text(),
                "date": cols[1].inner_text(),
                "amount": cols[2].inner_text(),
                "status": cols[3].inner_text(),
            })

        browser.close()

    return orders

if __name__ == "__main__":
    data = extract_orders_portal("my_username", "my_password")
    print(json.dumps(data, indent=2))
```

Key points in this script: `headless=True` runs the browser without a visible window (ideal for servers). `wait_for_url` and `wait_for_selector` avoid race conditions — the most common error in fragile RPA scripts is advancing before the page has loaded.

## Desktop Automation: Spreadsheets, PDFs, and Legacy Systems

For desktop systems, PyAutoGUI is the path. The most robust approach uses `pyautogui.locateOnScreen()` — instead of fixed coordinates, you pass a screenshot of the button/field you want to click and PyAutoGUI finds where it is on the current screen:

```python
import pyautogui
import time

def fill_erp_form(data: dict):
    # Opens the system via shortcut or double-click on icon
    pyautogui.hotkey("win", "r")
    pyautogui.write("C:\\SystemERP\\erp.exe", interval=0.05)
    pyautogui.press("enter")
    time.sleep(3)  # waits for the system to open

    # Locate the "Customer Code" field by reference image
    customer_code_field = pyautogui.locateOnScreen(
        "assets/customer_code_field.png",
        confidence=0.9  # 90% similarity tolerance
    )

    if customer_code_field:
        pyautogui.click(customer_code_field)
        pyautogui.write(data["customer_code"], interval=0.05)
        pyautogui.press("tab")
        pyautogui.write(data["name"], interval=0.05)
        pyautogui.hotkey("ctrl", "s")  # save
    else:
        raise RuntimeError("'Customer Code' field not found on screen")
```

For Excel spreadsheets, PyAutoGUI isn't even needed: `openpyxl` reads and writes `.xlsx` files directly, without opening Excel. For text PDFs, `pdfplumber` extracts content with precision. These libraries are faster, more reliable, and don't depend on the screen.

## Scheduling with Cron and Failure Monitoring

An RPA script that runs once manually has limited value. The real value comes from scheduled scripts that run on their own — every night, every hour, every 15 minutes.

On Linux and macOS, the native scheduler is cron. For a Python script that runs every day at 6am:

```bash
# edit with: crontab -e
# minute hour day month weekday command
0 6 * * * /usr/bin/python3 /home/user/rpa/extract_orders.py >> /var/log/rpa/orders.log 2>&1
```

On Windows, Task Scheduler does the same. For more serious projects, libraries like `APScheduler` let you define schedules directly in Python code with timezone support, job persistence, and error callbacks.

Failure monitoring is where most amateur scripts fail silently. The minimum solution is to send an alert on exception:

```python
import traceback
import smtplib
from email.message import EmailMessage

def send_error_alert(error: Exception, context: str):
    msg = EmailMessage()
    msg["Subject"] = f"[RPA] Failure in: {context}"
    msg["From"] = "rpa@company.com"
    msg["To"] = "team@company.com"
    msg.set_content(f"Error:\n{traceback.format_exc()}")

    with smtplib.SMTP("smtp.company.com", 587) as smtp:
        smtp.login("user", "password")
        smtp.send_message(msg)

def run_with_retry(func, attempts=3, context=""):
    for i in range(attempts):
        try:
            return func()
        except Exception as e:
            if i == attempts - 1:
                send_error_alert(e, context)
                raise
```

For those who prefer ready-made solutions, Sentry monitors Python exceptions in production with full context (stack trace, local variables, breadcrumbs) and integrates with Slack and PagerDuty.

## Conclusion

RPA with Python isn't the solution for everything, but it is the right solution for repetitive processes in systems without an available API. The combination of Playwright for web, PyAutoGUI for desktop, cron scheduling, and failure monitoring covers 90% of the use cases mid-sized companies face — without the license cost of enterprise platforms.

The secret is writing resilient scripts: auto-wait instead of fixed sleeps, image-based location instead of coordinates, retry with failure notification. Well-written scripts run for months without intervention.
