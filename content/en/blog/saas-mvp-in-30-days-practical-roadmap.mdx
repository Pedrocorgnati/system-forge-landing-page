30 days is enough to validate a hypothesis. Not to build a product. That distinction defines everything in the SaaS MVP development process.

The goal of an MVP isn't to deliver a complete product — it's to discover whether people will pay to solve the problem you're attacking. Everything that doesn't contribute to that answer is waste. But that doesn't mean building something broken: a technically poor MVP generates debt that stalls growth for months after validation.

This roadmap divides the 30 days into four weeks with clear objectives, and defines what's essential, what can wait, and why each decision matters.

## Week 1: Stack, Auth, and Multi-Tenancy Structure

The first week is about the foundation — the technical decisions that will be most expensive to change later.

**Stack selection for SaaS MVP in 2024:**

For most cases, Next.js with App Router is the best choice for a SaaS MVP's frontend and API:
- Full-stack in a single codebase
- Server Components reduce JavaScript sent to the client
- API Routes for simple endpoints, Server Actions for forms
- Deploy on Vercel in minutes

For the database, PostgreSQL via Supabase or Neon eliminates all infrastructure ops in the early stages.

```
Recommended SaaS MVP stack:

Frontend / API:  Next.js 14+ (App Router)
Database:        PostgreSQL (Supabase or Neon)
ORM:             Prisma or Drizzle
Auth:            NextAuth.js v5 or Clerk
Billing:         Stripe Billing
Deploy:          Vercel
Email:           Resend
```

**Auth in week 1 — don't push it off:**

Auth seems simple and never is. Magic link, Google OAuth, session management, protected route middleware — all of this needs to be working before any product feature. Trying to implement auth with half-baked business features is a recipe for rework.

**Minimal multi-tenancy:**

In week 1, implement the simplest model: shared database with `organization_id` in all tables and Row Level Security in PostgreSQL. Don't build schema-per-tenant in the MVP — the complexity isn't justified with fewer than 100 customers.

```sql
-- Minimal multi-tenancy schema for MVP
CREATE TABLE organizations (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name       TEXT NOT NULL,
  slug       TEXT UNIQUE NOT NULL,
  plan       TEXT DEFAULT 'trial',
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE organization_members (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id UUID NOT NULL REFERENCES organizations(id),
  user_id         UUID NOT NULL,
  role            TEXT NOT NULL DEFAULT 'member', -- 'owner', 'admin', 'member'
  created_at      TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(organization_id, user_id)
);
```

## Week 2: Core Feature and Minimal Dashboard

The core feature is the reason the product exists. Everything this week should be about implementing the main user flow — start to finish — without polish, but working.

Week 2 rule: **no configuration features**. Don't implement account settings, profile customization, themes, notifications, or data exports. Only the main flow.

Minimum viable dashboard:

An MVP dashboard needs to show three things: the current state of the main data, what the user should do next (onboarding guidance), and quick access to the most common actions. A single well-designed screen is sufficient.

| Week | Focus | What NOT to do |
|------|-------|----------------|
| 1 | Auth + multi-tenancy + infra | Product features |
| 2 | Core feature end-to-end | Configurations, polish |
| 3 | Billing + onboarding | Secondary features |
| 4 | Polish + feedback | Rewrites, refactoring |

## Week 3: Billing and Onboarding

Billing in week 3 — not week 4, not "after launch." If you launch without billing, you're not validating whether people pay. You're validating whether people use something for free, which answers a completely different question.

**Minimal billing with Stripe:**

For the MVP, you need only three things from Stripe:
1. A plan with a 14-day trial (with or without card)
2. `customer.subscription.updated` webhook to update organization status in the database
3. Subscription management link (Stripe Customer Portal) — eliminates the need to build billing UI

```javascript
// Creating Stripe Customer Portal session
// Replaces all billing UI in the MVP
app.get('/billing/portal', requireAuth, async (req, res) => {
  const session = await stripe.billingPortal.sessions.create({
    customer: req.user.organization.stripeCustomerId,
    return_url: `${process.env.APP_URL}/dashboard`,
  });
  res.redirect(session.url);
});
```

The Stripe Customer Portal handles upgrade, downgrade, card changes, invoice downloads, and cancellation — without writing a single line of billing UI.

**Onboarding in week 3:**

With the product working, week 3 is the right time to build onboarding: the first-steps checklist, empty states, and the welcome email with activation sequence. The welcome email alone measurably increases activation — implement with Resend in under half a day.

## Week 4: Polish, Testing, and First Users

Week 4 is not about new features. It's about removing friction from what already exists and getting the first real users using the product.

**What to polish in week 4:**
- Loading states on all actions that make network calls
- Clear error messages (not "Something went wrong")
- Basic mobile responsiveness
- SEO metadata on main pages
- Favicon and og:image

**First users:**

The first 10-20 users shouldn't come from ads — they should come from direct conversations. Join niche communities, post on your networks, message people you know have the problem the product solves. Offer the trial period and explicitly ask for feedback.

Install a session recording tool (Hotjar, Microsoft Clarity — free plan) before sharing the link. The recordings from the first sessions of real users are more valuable than any assumption about what to improve.

## Conclusion

30 days is a fair deadline to have a SaaS MVP live, with auth, basic multi-tenancy, working core feature, integrated billing, and minimal onboarding. It's not time for a perfect product — but it's enough to have something real in the first users' hands and start collecting the data that informs what to build next.
