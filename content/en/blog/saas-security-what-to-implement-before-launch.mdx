A security breach right after launch can end a SaaS before it even has a chance to prove its value. Not necessarily because the attack is catastrophic in scale — but because reputation is the most fragile asset of a new product. A customer data leak in the first month of operation is rarely recoverable.

The good news is that most vulnerabilities exploited in new SaaS products aren't sophisticated zero-days. They're basic, predictable flaws: passwords without attempt limits, tokens exposed in logs, missing permission validation on API endpoints, sensitive data without encryption. Fixing these vulnerabilities before launch is demanding but entirely feasible.

This guide covers the five security layers every SaaS must have implemented before welcoming its first real users.

## Authentication: MFA, Session Management, and Brute Force

Authentication is the front door — and most successful attacks start here. Implementing secure authentication goes beyond "verify email and password."

**MFA (Multi-Factor Authentication):**

For B2B SaaS, MFA isn't optional — it's expected. Enterprise customers frequently require TOTP support (Google Authenticator, Authy) as a security requirement. The implementation can be done with libraries like `otplib` (Node.js) in less than a day.

```javascript
import { authenticator } from 'otplib';
import { toDataURL } from 'qrcode';

// Generate secret and QR Code for the user to configure MFA
async function setupMFA(userId: string) {
  const secret = authenticator.generateSecret();
  const otpauth = authenticator.keyuri(userEmail, 'MySaaS', secret);
  const qrCodeUrl = await toDataURL(otpauth);

  // Save encrypted secret in the database (never in plain text)
  await db.user.update({
    where: { id: userId },
    data: { mfaSecret: encrypt(secret), mfaEnabled: false }, // activate only after verification
  });

  return { qrCodeUrl, secret };
}

// Verify TOTP code on login
function verifyMFAToken(secret: string, token: string): boolean {
  return authenticator.check(token, secret);
}
```

**Brute force protection:**

Every login endpoint needs specific rate limiting per IP and per email. Without it, automated tools test thousands of passwords in seconds.

```javascript
// Rate limiting on the login endpoint
import rateLimit from 'express-rate-limit';

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15-minute window
  max: 5,                    // maximum 5 attempts per IP
  message: 'Too many attempts. Try again in 15 minutes.',
  standardHeaders: true,
  legacyHeaders: false,
});

app.post('/auth/login', loginLimiter, handleLogin);
```

**Session Management:**

- JWT tokens with 15-60 minute expiration for access tokens
- Refresh tokens with rotation — each use invalidates the previous one
- Session revocation on password change or suspicious activity detection
- HttpOnly cookies to store tokens in the browser (never localStorage for sensitive access tokens)

## Authorization: RBAC and Least Privilege Principle

Authentication verifies *who* the user is. Authorization verifies *what they can do*. These are different problems, and confusing them is one of the most common sources of SaaS vulnerabilities.

**RBAC (Role-Based Access Control):**

Implement clear roles from the start. For most B2B SaaS, three roles are sufficient in the MVP:

| Role | Typical permissions |
|------|---------------------|
| Owner | Everything, including billing and deleting the organization |
| Admin | Manage members, settings, all data |
| Member | Create and edit own records, view team's |
| Viewer (optional) | Read-only |

**Permission check on ALL endpoints:**

The most common mistake is checking authentication (is the user logged in?) but not authorization (does the user have permission for this specific resource?). A member with access to organization A should never be able to read or modify organization B's data — even when authenticated.

```typescript
// Authorization middleware per resource
async function requireOrganizationAccess(
  req: Request,
  res: Response,
  next: NextFunction
) {
  const { organizationId } = req.params;
  const userId = req.user.id;

  const membership = await db.organizationMember.findUnique({
    where: { organizationId_userId: { organizationId, userId } },
  });

  if (!membership) {
    return res.status(403).json({ error: 'Access denied' });
  }

  req.membership = membership; // role available for the handler
  next();
}
```

## Encryption: Data at Rest and in Transit

**In transit:** HTTPS mandatory on all endpoints. No exceptions. Configure HSTS (HTTP Strict Transport Security) to force HTTPS even if someone tries to access via HTTP.

**At rest:** Not all data needs encryption in the database, but sensitive data does:

- Passwords: never store in plain text or with reversible encryption. Use bcrypt, Argon2, or scrypt with salt
- MFA secrets and API keys: symmetric encryption with externally managed key (AWS KMS, Vault, environment variable)
- Sensitive personal data (health data, financial data): field-level encryption when required by HIPAA/GDPR

```typescript
// Field encryption with AES-256-GCM
import { createCipheriv, createDecipheriv, randomBytes } from 'crypto';

const ALGORITHM = 'aes-256-gcm';
const KEY = Buffer.from(process.env.ENCRYPTION_KEY!, 'hex'); // 32 bytes

export function encrypt(text: string): string {
  const iv = randomBytes(16);
  const cipher = createCipheriv(ALGORITHM, KEY, iv);
  const encrypted = Buffer.concat([cipher.update(text, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();
  return `${iv.toString('hex')}:${tag.toString('hex')}:${encrypted.toString('hex')}`;
}

export function decrypt(data: string): string {
  const [ivHex, tagHex, encryptedHex] = data.split(':');
  const decipher = createDecipheriv(ALGORITHM, KEY, Buffer.from(ivHex, 'hex'));
  decipher.setAuthTag(Buffer.from(tagHex, 'hex'));
  return decipher.update(Buffer.from(encryptedHex, 'hex')) + decipher.final('utf8');
}
```

## Rate Limiting, WAF, and Security Headers

**Rate limiting on all public routes:**

Not just on login. Account creation endpoints, password recovery, invite sending, any route that can be abused by automation needs rate limiting.

**HTTP security headers:**

A complete security headers configuration takes minutes to implement and blocks an entire class of attacks (XSS, clickjacking, MIME sniffing):

```javascript
// next.config.js — security headers
const securityHeaders = [
  { key: 'X-DNS-Prefetch-Control', value: 'on' },
  { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
  { key: 'X-Frame-Options', value: 'SAMEORIGIN' },
  { key: 'X-Content-Type-Options', value: 'nosniff' },
  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
  {
    key: 'Content-Security-Policy',
    value: "default-src 'self'; script-src 'self' 'unsafe-eval' 'unsafe-inline'; ...",
  },
];
```

**Pre-launch security checklist:**

| Item | Priority |
|------|---------|
| HTTPS + HSTS on all endpoints | Required |
| Rate limiting on login and public routes | Required |
| Passwords with bcrypt/Argon2 | Required |
| Authorization check on all endpoints | Required |
| HTTP security headers configured | Required |
| Environment variables never in repository | Required |
| MFA available (not required in MVP) | Recommended |
| Sensitive field encryption | Recommended |
| Security audit logs | Recommended |
| Dependency scan (npm audit) | Recommended |

## Conclusion

Security isn't a feature to add later — it's a layer that permeates the entire architecture. The required items on this list take two to four days to implement correctly in a new SaaS. Those are days worth years of protected reputation.

The cost of remediating a security breach after an incident — customer notification, potential GDPR/HIPAA exposure, emergency technical rework — is orders of magnitude higher than the cost of implementing these protections before launch.
