## 95% of Exploited Vulnerabilities Are Known and Avoidable

Most successful attacks don't exploit sophisticated zero-days. They exploit known, documented flaws that could have been prevented with basic secure development practices. OWASP (Open Web Application Security Project) has been documenting the most critical web application vulnerabilities since 2003, and the same categories keep appearing repeatedly.

This article covers the 10 most common vulnerabilities, with practical examples and how to fix them.

## 1. Injection (SQL, NoSQL, Command)

Injection occurs when untrusted data is sent to an interpreter as part of a command or query.

**SQL Injection — vulnerable example:**

```javascript
// NEVER do this
const query = `SELECT * FROM users WHERE email = '${email}' AND password = '${password}'`;
```

If the user enters `' OR '1'='1` as email, the query returns all users.

**Fix — parameterized queries:**

```javascript
// Correct: parameters separated from the query
const result = await db.query(
  'SELECT * FROM users WHERE email = $1 AND password = $2',
  [email, hashedPassword]
);
```

Modern ORMs like Prisma and Drizzle use parameterized queries by default. Risk arises when developers use `$queryRaw` or build SQL manually.

## 2. Broken Authentication and Session Management

Authentication flaws include: weak passwords without strength policy, missing rate limiting on login, predictable session tokens, sessions that never expire.

**Common problems:**

- Passwords stored in plain text or with MD5/SHA1 hash
- Absence of two-factor authentication for critical operations
- JWT tokens without expiration or with weak secret
- Session fixation — session ID reuse after login

**Fix:**

```typescript
// Correct hash with bcrypt (minimum cost 10)
import bcrypt from 'bcryptjs';

const SALT_ROUNDS = 12;
const hashedPassword = await bcrypt.hash(plainPassword, SALT_ROUNDS);

// JWT with short expiration and refresh token
const token = jwt.sign(
  { userId: user.id },
  process.env.JWT_SECRET!,
  { expiresIn: '15m' }
);
```

## 3. Sensitive Data Exposure

Exposed sensitive data includes passwords, API tokens, personal data (SSN, credit card), health data, and financial data stored or transmitted without adequate protection.

**Common mistakes:**
- Sensitive data in application logs
- API keys in the Git repository
- Cached data without TTL or without encryption
- HTTP communication instead of HTTPS

**Fix:**
- Never log sensitive data (`console.log(user)` can expose passwords)
- Use `.gitignore` for `.env` and never commit secrets
- Encrypt sensitive data at rest with AES-256
- Force HTTPS in all environments

## 4. XML External Entities (XXE)

Affects applications that process XML. An attacker can read files from the server, make internal requests (SSRF), or cause denial of service.

**Fix:** Disable external entity processing in the XML parser. In modern applications using JSON, risk is minimal — but legacy APIs still process XML.

## 5. Broken Access Control

Occurs when users can perform actions beyond their permissions. Includes IDOR (Insecure Direct Object Reference) — accessing other users' resources by changing an ID in the URL.

**Vulnerable example:**

```typescript
// Vulnerable: doesn't check if the order belongs to the logged-in user
app.get('/orders/:orderId', async (req, res) => {
  const order = await db.order.findUnique({ where: { id: req.params.orderId } });
  res.json(order);
});
```

**Fix:**

```typescript
// Correct: verifies resource ownership
app.get('/orders/:orderId', authenticate, async (req, res) => {
  const order = await db.order.findUnique({
    where: { id: req.params.orderId, userId: req.user.id } // userId filters by logged-in user
  });
  if (!order) return res.status(404).json({ error: 'Not found' });
  res.json(order);
});
```

## 6. Security Misconfiguration

Insecure default configurations, excessive permissions, missing HTTP headers, unnecessary open ports.

**Essential security headers:**

```typescript
// Next.js — next.config.js
const securityHeaders = [
  { key: 'X-Content-Type-Options', value: 'nosniff' },
  { key: 'X-Frame-Options', value: 'DENY' },
  { key: 'X-XSS-Protection', value: '1; mode=block' },
  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
  {
    key: 'Content-Security-Policy',
    value: "default-src 'self'; script-src 'self' 'unsafe-inline'"
  }
];
```

## 7. Cross-Site Scripting (XSS)

XSS allows attackers to inject malicious scripts into pages viewed by other users. Can be used to steal session cookies, redirect users, or modify page content.

**Types of XSS:**
- **Stored XSS:** Script saved in the database and shown to other users
- **Reflected XSS:** Script in URL reflected in the response
- **DOM-based XSS:** DOM manipulation via client-side JavaScript

**Fix:** Modern frameworks like React escape content automatically. Risk arises with `dangerouslySetInnerHTML` or direct DOM manipulation with `innerHTML`.

```typescript
// Dangerous
element.innerHTML = userInput;

// Safe
element.textContent = userInput;
// Or, if you need HTML, use a sanitization library like DOMPurify
element.innerHTML = DOMPurify.sanitize(userInput);
```

## 8. Insecure Deserialization

Deserializing untrusted data can result in remote code execution. Primarily affects languages like Java and PHP, but also JavaScript with `JSON.parse` combined with prototypes.

**Fix:** Validate and sanitize deserialized data with schemas (Zod, Joi) before processing.

## 9. Using Components with Known Vulnerabilities

Outdated dependencies with known CVEs are a direct attack vector. Most projects have dozens of indirect dependencies that are rarely audited.

**Mandatory practice:**

```bash
# Audit dependencies regularly
npm audit

# Fix vulnerabilities automatically (when possible)
npm audit fix

# Check licenses and vulnerabilities with dedicated tool
npx snyk test
```

Configure automatic alerts on GitHub (Dependabot) to receive automatic PRs when dependencies with CVEs are identified.

## 10. Insufficient Logging and Monitoring

Without proper logs, ongoing attacks go unnoticed for days or weeks. Without alerts, you discover the problem when the customer complains.

**What to log:**
- Authentication attempts (success and failure)
- Permission changes and sensitive data access
- Authorization errors (403) — may indicate IDOR attempts
- Anomalous request spikes

**What NOT to log:**
- Passwords (not even as hashes)
- Full session tokens
- Sensitive personal data (SSN, credit card)

## Conclusion

Security is not an additional feature — it's part of professional development. The 10 OWASP Top 10 categories represent avoidable vulnerabilities with basic practices: parameterized queries, input validation, server-side access control, updated dependencies, and correct headers.
