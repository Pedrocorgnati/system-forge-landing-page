# Backend Urgente: API e Infraestructura de Servidor en Semanas

Si necesitas backend urgente, la decisión más impactante es: construir desde cero o usar BaaS (Backend as a Service). Supabase o Firebase resuelven autenticación, base de datos y APIs básicas en días, costando entre 3.000 € y 12.000 € de setup. Backend custom con Node.js o Python cuesta 15.000–55.000 € y lleva 4–10 semanas, pero ofrece control total. Para urgencia máxima, la estrategia es usar BaaS para el MVP y migrar a custom cuando el producto valide. La regla: no reinventes lo que ya existe.

Trabajo con backend para PYMEs y startups cada semana. Frontend listo sin API, backend legacy en PHP que no aguanta carga, dev backend que salió en medio del proyecto. Ya he visto todos los escenarios. Lo que diferencia un proyecto que entrega en semanas de uno que se arrastra por meses es la claridad en las decisiones de arquitectura — y la disciplina de no hacer overengineering en el MVP. Te muestro cómo tomar esas decisiones.

## Qué Hacer Cuando Necesitas Backend con Urgencia

Antes de contratar, define el alcance técnico. Estas preguntas determinan la arquitectura:

**1. ¿Qué necesita hacer el backend?** Lista los endpoints necesarios. "API para la app" no es alcance. "15 endpoints REST para CRUD de usuarios, productos y pedidos + autenticación + subida de imágenes" sí lo es.

**2. ¿Cuál es el frontend?** React, Next.js, Flutter, React Native? Eso define el formato de la API (REST, GraphQL) y los patrones de comunicación.

**3. ¿Cuál es el volumen esperado?** 100 peticiones al día y 100.000 al día exigen arquitecturas completamente diferentes. Para la mayoría de las PYMEs españolas, el volumen real es bajo — y BaaS resuelve.

**4. ¿Qué integraciones necesitas?** Pasarela de pago, Verifactu, facturación electrónica, WhatsApp Business API, servicio de email, Bizum? Cada integración añade 1–2 semanas al proyecto.

**5. ¿Existe base de datos?** Migrar datos de hoja de cálculo a base de datos estructurada es un proyecto dentro del proyecto. Define eso antes de empezar.

## Backend From Scratch vs BaaS (Supabase, Firebase): Qué Acelera Más

Esta es la decisión que define el plazo del proyecto. Vamos al grano:

**BaaS (Supabase recomendado):**
- Autenticación lista (email, OAuth, magic link) — 0 líneas de código
- Base de datos PostgreSQL con API automática — creas tabla, ganas endpoints
- Row Level Security — permisos a nivel de base de datos, sin middleware custom
- Storage para uploads — integrado al auth
- Edge Functions para lógica de negocio compleja
- Setup: 1–3 días para el core, 1–3 semanas para el MVP completo
- Coste: 3.000–12.000 € de setup

**Backend custom (Node.js/Express o Python/FastAPI):**
- Control total de la arquitectura y rendimiento
- Lógica de negocio compleja sin limitaciones
- Integraciones ilimitadas con APIs externas
- Tests unitarios y de integración completos
- CI/CD y deploy automatizado
- Setup: 4–10 semanas para MVP
- Coste: 15.000–55.000 €

**Cuándo usar BaaS:** el MVP necesita estar en el aire en días/semanas, volumen es bajo-medio (hasta 10.000 usuarios), reglas de negocio son CRUD + auth + permisos, el equipo es pequeño (1–2 devs).

**Cuándo usar custom:** reglas de negocio complejas (cálculos financieros, algoritmos propietarios), integraciones profundas con sistemas legacy, requisitos regulatorios específicos (PCI-DSS, HIPAA en entornos médicos), volumen alto con requisitos de rendimiento.

### Supabase Como Backend Acelerador: Qué Resuelve (y Qué No)

Uso Supabase como stack estándar para MVPs en SystemForge. Lo que resuelve bien: autenticación completa, CRUD con API automática, permisos granulares (RLS), storage de archivos, realtime (websockets) y edge functions para lógica custom.

Lo que no resuelve: lógica de negocio muy compleja (mejor en backend dedicado), procesamiento pesado (ETL, ML), colas de tareas asíncronas e integraciones que exigen SDKs nativos pesados.

Supabase crece un 300 % anual en adopción (State of Backend 2025), y la curva de adopción en España aceleró en los últimos 12 meses. Es open-source: puedes self-host en cualquier momento, eliminando vendor lock-in. Esto es especialmente relevante bajo GDPR: al poder autoalojar en infraestructura europea (OVH, Hetzner, AWS Frankfurt), mantienes los datos bajo jurisdicción UE.

## Arquitectura de Backend Para Proyectos Urgentes: Decisiones Pragmáticas

### Node.js vs Python vs Go: Qué Stack Para Backend Rápido

| Criterio | Node.js (Express/Fastify) | Python (FastAPI/Django) | Go |
|----------|--------------------------|------------------------|-----|
| Velocidad de desarrollo | Alta | Alta | Media |
| Rendimiento | Buena | Buena (async) | Excelente |
| Ecosistema ES | Grande | Grande | Pequeño |
| Curva de aprendizaje | Baja | Baja | Media |
| Ideal para | APIs REST, real-time | Data-heavy, ML, APIs | Alta concurrencia |
| Plazo MVP | 4–6 semanas | 4–8 semanas | 6–10 semanas |

Para proyectos urgentes de PYME, Node.js y Python son las elecciones pragmáticas. Go solo se justifica cuando el rendimiento extremo es requisito desde el día 1 (trading de alta frecuencia, procesamiento masivo).

En SystemForge usamos Node.js (con TypeScript) como estándar para APIs REST y Python (FastAPI) cuando el proyecto tiene componente de datos pesado. La decisión es por productividad, no por preferencia.

### APIs RESTful vs GraphQL: Qué Elegir Cuando el Plazo Aprieta

REST. Para proyectos urgentes, REST es la respuesta en el 90 % de los casos. GraphQL añade complejidad de setup, herramientas y debugging que no se justifica cuando tienes 1 frontend consumiendo la API. GraphQL tiene sentido cuando múltiples clientes (web, móvil, partners) consumen la misma API con necesidades diferentes de datos. Para MVP de PYME, REST con buena paginación y filtros resuelve.

### Autenticación, Autorización y Seguridad: Qué No Se Puede Recortar

Backend urgente no es backend sin seguridad. El mínimo del día 1:

- **Autenticación:** JWT con refresh tokens o sesiones seguras. Nunca implementes auth desde cero — usa bibliotecas testadas (Passport.js, NextAuth, Supabase Auth).
- **Autorización:** RBAC (Role-Based Access Control) como mínimo. Cada endpoint verifica permiso.
- **Validación de inputs:** Zod o Joi en el backend. Nunca confíes en datos del frontend.
- **Rate limiting:** protección contra abuso de API. 5 minutos de configuración que evitan incidentes.
- **HTTPS:** obligatorio. Sin excepciones.
- **GDPR:** desde el día 1. Minimización de datos, consentimiento documentado, DPA con proveedores cloud. Un backend que procesa datos personales de clientes españoles debe cumplir RGPD.

## Errores de Arquitectura Que Parecen Rápidos Pero Cuestan Caro Después

**No implementar tests desde el día 1.** Backend urgente no es backend sin tests. Tests de integración en los endpoints críticos (auth, pago, datos sensibles) llevan 2–3 días extra y evitan semanas de debugging en producción. Pipeline de CI/CD con tests automatizados es parte del MVP.

**Database design "después normalizamos".** Índices, foreign keys y constraints se definen en la v1 o nunca. Migrar base de datos mal estructurada con datos de producción es 5 veces más caro que proyectar correctamente desde el inicio. Gasta 2–3 días en el schema antes de escribir la primera línea de código.

**Monolito gigante "porque es más rápido".** Un monolito bien organizado (controllers, services, repositories) es perfectamente válido para MVP. Un monolito donde todo está en 3 archivos gigantes es deuda técnica que cobra intereses compuestos. Separación de concerns no añade plazo — falta de separación añade caos.

**Ignorar logs y monitorización.** Sin logs estructurados, cuando algo se rompe en producción no sabes qué pasó. Sentry (error tracking) + logs JSON + health check endpoint llevan 1 día para configurar y son esenciales desde el deploy.

### Database Design Para Escalar: Decisiones Que No Puedes Errar en la v1

- Índices en todas las columnas usadas en WHERE y JOIN
- Foreign keys con constraints — integridad referencial en la base, no en el código
- Timestamps (created_at, updated_at) en toda tabla
- Soft delete (deleted_at) en vez de DELETE físico para datos de negocio
- UUID en vez de auto-increment para IDs expuestos en la API
- Separación clara entre datos de negocio y datos de aplicación

## Cuándo Contratar Backend Dedicado vs Full-Stack

**Contrata full-stack cuando:** el proyecto es un sistema web completo (frontend + backend), el equipo es pequeño y el plazo es ajustado. Un dev full-stack senior entrega MVP de punta a punta en 4–8 semanas.

**Contrata backend dedicado cuando:** el frontend ya existe y necesita API, el backend tiene complejidad técnica alta (algoritmos, integraciones pesadas), o ya tienes dev frontend y necesitas especialista en infraestructura.

Dev backend senior cuesta 35.000–55.000 €/año en el mercado español. Para proyecto puntual de 4–10 semanas, contratación por proyecto (15.000–55.000 €) tiene más sentido que contrato indefinido. Para mantenimiento continuado, contrato mensual o equipo interno.

Para proyectos que necesitan sistema web completo (front + back), consulta también nuestro artículo sobre desarrollo web moderno.

## Conclusión

Backend urgente exige pragmatismo: BaaS (Supabase) para MVPs que necesitan estar en el aire en días, custom (Node.js/Python) para proyectos con reglas de negocio complejas. En ambos casos, no recortes seguridad, tests y database design — esas decisiones no se pueden "añadir después". La inversión de 3.000–55.000 € entrega infraestructura que sostiene el negocio por años cuando las bases son correctas.

## Preguntas Frecuentes

### ¿BaaS como Supabase no genera vendor lock-in?

Supabase es open-source y corre en PostgreSQL estándar. Puedes hospedar por tu cuenta (self-hosted) en cualquier momento, llevando tus datos y schema sin alteración. Firebase sí genera lock-in significativo con Firestore y Cloud Functions propietarias. Para quien quiere velocidad sin lock-in, Supabase es la elección.

### ¿Backend hecho rápido aguantará escala?

Depende de las decisiones de arquitectura, no del plazo. Database design correcto, índices, caché y separación de concerns se hacen desde el día 1 o nunca. No existe "añadir rendimiento después". Un MVP bien arquitectado con Supabase soporta 50.000 usuarios sin ajustes. A partir de ahí, optimizaciones puntuales resuelven.

### ¿No sería mejor contratar dev backend fijo?

Para proyecto puntual de 4–10 semanas, no. Dev backend senior cuesta 35.000–55.000 €/año más cargas sociales. Contratación por proyecto (15.000–55.000 €) entrega resultado sin compromiso laboral. Para mantenimiento continuado tras el lanzamiento, contrato mensual de 1.200–4.000 €/mes con SLA tiene más sentido.

### ¿Necesito backend si ya uso Supabase?

Supabase ES tu backend para el 80 % de los casos de PYME. Autenticación, base de datos con API automática, storage y edge functions cubren la mayoría de los requisitos. Solo necesitas backend adicional (Node.js/Python) cuando tienes lógica de negocio que no cabe en edge functions o integraciones pesadas con sistemas legacy.

### ¿Cuál es la diferencia entre backend y sistema web?

Backend es la parte invisible: API, base de datos, lógica de negocio en el servidor. Sistema web es el paquete completo: frontend (lo que ve el usuario) + backend (lo que procesa los datos). Si necesitas los dos, el proyecto es sistema web. Si ya tienes frontend y necesitas la "máquina" de detrás, el proyecto es backend.

### ¿Backend urgente puede tener CI/CD y tests automatizados?

Debe tenerlo. Pipeline de CI/CD (GitHub Actions, por ejemplo) lleva 1 día para configurar. Tests de integración en los endpoints críticos llevan 2–3 días. Estas inversiones de 3–4 días eliminan semanas de debugging manual en producción y son parte del alcance mínimo de cualquier backend profesional.
