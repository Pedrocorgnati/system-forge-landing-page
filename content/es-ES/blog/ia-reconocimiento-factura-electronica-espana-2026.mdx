# IA para Reconocimiento de Facturas Electronicas en Espana 2026: OCR, Parsing y Casacion Automatica

Procesar manualmente las facturas que llegan a una PYME espanola consume entre 4 y 8 minutos por factura, con un margen de error humano del 5-12% y una proporcion media de 200 a 2.000 facturas mes en empresas de 50-300 empleados. Aplicar IA al pipeline de facturas recibidas, no las emitidas que cubre Verifactu, reduce ese tiempo a 15-40 segundos por factura con precision del 95-98% en campos clave. Coste por factura procesada: entre 0,005 y 0,030 euros usando Claude 4.7 Haiku o GPT-5-mini en 2026. La inversion para implantar el modulo va de 6.000 a 18.000 euros segun el stack que ya tengas.

*Por Pedro Corgnati, consultor brasileno full-stack que ha implementado modulos OCR + LLM en gestorias espanolas y departamentos financieros de PYMES desde 2024. Esta guia tiene los numeros reales, sin promesas de marketing.*

## El problema real: factura recibida no es factura emitida

Verifactu obliga al EMISOR de la factura a registrarla y firmarla. Pero el RECEPTOR de la factura, tu empresa cuando compras a proveedor, sigue recibiendo PDFs por email, fotos por WhatsApp del comercial que paso por el almacen, papeles escaneados que llegan en sobre. La factura electronica B2B obligatoria por la Ley Crea y Crece avanza despacio, con plazos extendidos hasta 2027/2028 segun tipo de empresa.

Mientras tanto, tu equipo administrativo abre cada factura, lee el NIF del proveedor, copia el numero, copia el importe, copia la base imponible, copia la cuota IVA, busca el pedido de compra asociado, casa importe y proveedor en el ERP, marca como contabilizada. Cuatro a ocho minutos por factura. Errores acumulativos. Cuello de botella permanente.

## Tres niveles de complejidad de la factura recibida

No todas las facturas son iguales tecnicamente. Tu pipeline IA debe distinguir tres tipos:

### Facturae XML estructurado (10-25% del volumen)

La administracion publica espanola y proveedores grandes envian Facturae 3.2.x en XML firmado. Tu sistema parsea con XSD oficial (cero IA necesaria, parser determinista) y extrae todos los campos al 100% de precision. Ahorro inmediato: cero trabajo manual.

### PDF con texto seleccionable (40-55%)

Facturas de SaaS internacionales (Stripe, AWS, Google), proveedores tecnologicos, consultoras. PDF generado por software, texto extraible. `pdfplumber` (Python) o `pdf-parse` (Node) extraen texto crudo, despues un LLM con prompt estructurado extrae el JSON con precision del 95-98%.

### Imagen escaneada o PDF rasterizado (25-40%)

Facturas de proveedores tradicionales (suministros, servicios locales, autonomos), tickets, fotos por WhatsApp del comercial. Aqui necesitas OCR previo (Tesseract local barato, AWS Textract o Azure Document Intelligence cloud potentes) y despues LLM. Precision 80-90% en campos clave; siempre con cola de revision humana.

## Stack tecnico recomendado 2026

Pipeline completo de extremo a extremo:

```
[Email IMAP / WhatsApp / Drag-drop / Webhook]
            |
            v
[Pre-clasificacion: es factura? duplicada?]
            |
            v
[OCR si imagen] -> [Texto crudo]
            |
            v
[LLM extrae JSON estructurado]
            |
            v
[Validacion contra schema (Zod / Pydantic)]
            |
            v
[Casacion proveedor + pedido + importe en ERP]
            |
            v
[Confianza alta -> auto-contabilizado]
[Confianza media -> cola revision humana]
[Confianza baja -> revision obligatoria]
```

### Componentes concretos

- **Ingesta**: IMAP via `imap-flow` (Node) o `imapclient` (Python). WhatsApp Business API con webhook cuando proveedor manda foto. Drag-drop en panel web Next.js.
- **OCR**: Tesseract para volumen bajo y presupuesto cero. AWS Textract a 0,001-0,015 euros por pagina cuando volumen sube. Azure Document Intelligence con modelo prebuilt-invoice optimizado para facturas.
- **LLM**: Claude 4.7 Haiku via Anthropic API region Frankfurt (cumple RGPD UE). GPT-5-mini via Azure OpenAI region UE. Mistral Large si quieres soberania europea estricta.
- **Schema validation**: Zod en TypeScript, Pydantic en Python. Define el JSON esperado con campos obligatorios y tipos. El LLM puede equivocarse pero el schema lo atrapa.
- **Vector DB para RAG opcional**: pgvector sobre Postgres si manejas catalogo proveedores (el LLM consulta historico para mejorar matching). Mas detalle en [bases de datos vectoriales guia devs IA](/blog/bases-de-datos-vectoriales-guia-devs-ia).

## Casacion automatica con tu ERP

Una vez extraido el JSON, la magia de verdad es casarlo con el ERP. Reglas:

- Match por NIF proveedor + numero factura + importe debe ser exacto.
- Si NIF y numero coinciden pero importe difiere mas de 0,01 euros, alerta inmediata.
- Si NIF nuevo (proveedor no existe en maestro), crear ficha pendiente de validacion.
- Si pedido de compra abierto coincide con importe + proveedor, asociar automaticamente.
- Si supera limite de aprobacion, encolar para responsable correspondiente.
- Si encaja sin alarmas, marcar como contabilizada y notificar.

Stack ERP que conecta directo: API hacia Holded, Sage50, A3, ContaPlus, Anfix, Quipu, Xolo. Si tu ERP es a medida, expones endpoints REST y el modulo IA los consume. ## Precision esperada (sin marketing)

Numeros reales que veo en proyectos:

- **Facturae XML**: 100% precision en todos los campos. Es parser determinista, no IA.
- **PDF estructurado claro (Stripe, AWS, SaaS)**: 95-98% en campos clave (NIF, importe, IVA, fecha, numero). Los errores son casos limite (multi-divisa, retenciones complejas, multiples lineas con descuentos).
- **PDF feo / fotos**: 80-90%. Siempre con cola de revision humana obligatoria.

Cuando NO debe automatizarse al 100%: importes mayores a limite de aprobacion (5.000-50.000 EUR segun empresa), proveedores nuevos sin historico, facturas con retencion IRPF (riesgo error fiscal), facturas intracomunitarias con inversion sujeto pasivo. Estas siempre pasan por revision humana.

## RGPD y AI Act: que cumplir

Datos de tarjetas e IBAN aparecen en facturas. Tres reglas no negociables:

1. **LLM cloud en region UE obligatorio**: Anthropic AWS Frankfurt, Azure OpenAI Ireland o Sweden, Mistral Paris. Nada de OpenAI us-east directo si tienes datos personales.
2. **Minimizacion de retencion**: el contenido enviado al LLM se purga del lado del proveedor en plazos definidos (Anthropic: 30 dias por defecto, configurable). Tu sistema log retiene 90 dias y borra.
3. **AI Act 2026**: si la decision de contabilizar es totalmente automatica y supera limite, clasifica como sistema de riesgo limitado. Requiere transparencia (el usuario sabe que IA decidio), supervision humana sobre el limite, y logs de decision auditables.

## Errores reales en proyectos

Lista de fallos que he visto repetidos:

1. **Subir imagen sin pre-procesado**: foto torcida con flash crea OCR caos. Pre-procesar (deskew, contraste, recorte) antes de OCR ahorra 50% errores.
2. **No tener feedback loop humano**: cuando el revisor corrige un error, ese caso debe alimentar fine-tuning o ejemplos few-shot del prompt. Sin loop, la precision degrada con tipos nuevos de factura.
3. **Confiar 100% en el LLM para importes**: el LLM puede inventar 1.234,56 cuando ve 12,3456. Validacion cruzada con suma base + IVA = total es obligatoria.
4. **Sin cola de revision = bombazo contable**: el dia que el LLM equivoca un IVA del 21% por 4% en 50 facturas, tu trimestre IVA esta mal. La cola humana sobre los casos dudosos es seguro de vida.
5. **Procesar sin verificar duplicados**: la misma factura llega 3 veces (proveedor reenvia por seguridad). Sin chequeo de hash + numero + NIF, contabilizas tres veces.
6. **No registrar el modelo y version usado**: cuando dentro de 18 meses haya disputa por una factura mal contabilizada, necesitas saber que LLM en que version proceso ese registro.

## FAQ

**IA reemplaza al contable o al asesor?**
No. Reemplaza el trabajo mecanico de transcribir datos. El criterio contable, la decision sobre clasificacion fiscal de un gasto dudoso, la interpretacion de un acta de inspeccion AEAT, la planificacion fiscal del cliente, todo eso sigue siendo humano. El asesor que automatiza la entrada de datos puede atender 3 veces mas clientes con el mismo equipo.

**Que pasa con datos sensibles (IBAN, importes) en LLM cloud?**
LLM cloud en region UE bajo contrato con clausulas RGPD (Data Processing Agreement firmado con Anthropic o Microsoft) cumple. Anthropic y Azure OpenAI no usan los datos para entrenar modelos publicos cuando estas en plan empresa. Para casos extremos (banca, sanidad), LLM on-premise (Llama 3.3 70B en infraestructura propia) es opcion pero coste de hardware sube fuerte.

**Necesito cambiar mi ERP actual para integrar IA de facturas?**
No, en general. La mayoria de ERPs comerciales (Holded, Sage50, A3, ContaPlus, Anfix) tienen API o conector. Si tu ERP es a medida sin API, el modulo IA exige primero exponer endpoints. Coste extra: 2.000-5.000 EUR para construir API minima de proveedores + facturas + asientos.

**Cual es el porcentaje real de error que debo aceptar?**
Para automatizacion total: error menor al 0,5% en campos criticos (importe, IVA, NIF). Esto se consigue con cola de revision sobre el 5-15% de casos dudosos. Auto-contabilizando el 85-95% sin tocar nada y revisando manual el resto, llegas a esos numeros. Pretender 100% sin revision humana es promesa de marketing irreal.

**Funciona con facturas en otros idiomas (italiano, frances, portugues)?**
Si. LLMs modernos manejan multi-idioma nativamente. Una empresa espanola con proveedores europeos puede procesar facturas en 5-6 idiomas con la misma pipeline y prompts genericos. La unica adaptacion es validacion de formatos fiscales locales (P.IVA italiano, SIRET frances, NIPC portugues) en el schema.

**Las facturas Facturae siguen necesitando IA?**
No. Facturae es XML estructurado que parser determinista lee al 100%. Lo unico donde la IA podria ayudar en Facturae es categorizacion (que tipo de gasto es) o deteccion de anomalias (proveedor habitual factura 10x el importe normal este mes). Pero la extraccion en si es trivial sin IA.
