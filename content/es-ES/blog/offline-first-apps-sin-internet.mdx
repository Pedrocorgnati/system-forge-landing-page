Las apps que necesitan internet para funcionar pierden usuarios en el metro, en aviones, en zonas con cobertura deficiente y en todos los momentos en que la conexión oscila pero el usuario todavía quiere usar el producto. Esa pérdida no aparece de forma dramática — el usuario no desinstala en el momento de la caída de señal. Simplemente asocia la app con una experiencia frustrante y la abre cada vez menos.

El enfoque offline-first invierte la premisa: la app funciona completamente con los datos locales, y la sincronización con el servidor ocurre como un beneficio adicional, no como un requisito para usar el producto. Implementar esto correctamente requiere decisiones de arquitectura que deben tomarse temprano.

## WatermelonDB: Base de Datos Local Reactiva para React Native

WatermelonDB es la solución más madura para persistencia local en React Native. Está construida sobre SQLite, es reactiva (los componentes se actualizan automáticamente cuando cambian los datos) y tiene un sistema de sincronización diseñado específicamente para el problema offline-first.

La configuración básica define el schema y los modelos:

```typescript
const schema = appSchema({
  version: 1,
  tables: [
    tableSchema({
      name: 'tasks',
      columns: [
        { name: 'title', type: 'string' },
        { name: 'completed', type: 'boolean' },
        { name: 'synced_at', type: 'number', isOptional: true },
      ],
    }),
  ],
});
```

Los componentes se suscriben a queries reactivas que se actualizan automáticamente cuando los datos cambian — sin necesidad de gestionar estado manualmente.

## Estrategia de Sincronización

El protocolo de sincronización de WatermelonDB funciona con dos operaciones: `pullChanges` (trae los cambios del servidor desde el último sync) y `pushChanges` (envía los cambios locales al servidor).

```typescript
await synchronize({
  database,
  pullChanges: async ({ lastPulledAt }) => {
    const response = await api.get('/sync/pull', {
      params: { lastPulledAt }
    });
    return response.data; // { changes, timestamp }
  },
  pushChanges: async ({ changes }) => {
    await api.post('/sync/push', { changes });
  },
});
```

La sincronización puede ejecutarse: al volver a primer plano, cuando se detecta conectividad, en background a intervalos regulares, o de forma manual por el usuario. Para la mayoría de los casos, el enfoque de "sincronizar al volver al primer plano + al detectar conexión" es suficiente.

## Resolución de Conflictos

El caso más complejo del offline-first es cuando dos usuarios modifican el mismo registro sin estar conectados al mismo tiempo. Hay tres estrategias:

**Last Write Wins (LWW):** el cambio con timestamp más reciente gana. Simple de implementar, puede perder datos si dos usuarios editan el mismo campo.

**Merge por campos:** se comparan campo por campo y se aplican los cambios no conflictivos de ambas versiones. Los conflictos en el mismo campo requieren resolución manual o una regla determinista.

**CRDTs (Conflict-free Replicated Data Types):** estructuras de datos matemáticamente garantizadas para converger sin conflictos, sin importar el orden de aplicación de los cambios. Son más complejas de implementar pero la solución más robusta para documentos colaborativos.

## UX para Estados Sin Conexión

El diseño de la UX offline-first tiene reglas claras:

Nunca bloquear acciones por falta de conexión. El usuario puede crear, editar y eliminar — todo se procesa localmente y se sincroniza después. Sí mostrar claramente cuando el contenido está pendiente de sincronización (un indicador sutil, no un modal bloqueante). Gestionar conflictos de forma transparente cuando es posible, y notificar solo cuando requiere decisión del usuario.

Un indicador de estado de sincronización en la barra de navegación (nube con tick = sincronizado, nube con reloj = pendiente, nube con X = error) comunica el estado sin interrumpir el flujo de trabajo.
