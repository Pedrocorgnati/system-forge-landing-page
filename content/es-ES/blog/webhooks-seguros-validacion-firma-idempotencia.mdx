Los webhooks son uno de los patrones más potentes y más mal implementados en integraciones entre sistemas. La idea es simple: en lugar de consultar una API periódicamente ("¿hay novedades?"), el servicio externo te avisa cuando algo ocurre. ¿Pago aprobado? POST a tu endpoint. ¿Entrega confirmada? POST a tu endpoint.

El problema es que un endpoint de webhook sin protección es una puerta abierta. Cualquiera que descubra la URL puede enviar eventos falsos — un pago "aprobado" que nunca ocurrió, una devolución fabricada, una entrega confirmada de un pedido inexistente. Los ataques a webhooks mal configurados son relativamente comunes en sistemas de e-commerce.

## Validación de Firma HMAC-SHA256

La firma HMAC es el mecanismo estándar para verificar que el webhook proviene del servicio correcto y que el cuerpo no ha sido modificado en tránsito.

El servicio que envía el webhook incluye un header con la firma del cuerpo, calculada con una clave secreta que solo tú y ellos conocen. Tu endpoint verifica la firma antes de procesar el evento:

```typescript
import crypto from 'crypto';

function verifyWebhookSignature(
  payload: string,       // body como string, sin parsear
  signature: string,     // header X-Webhook-Signature
  secret: string         // clave secreta compartida
): boolean {
  const expectedSignature = crypto
    .createHmac('sha256', secret)
    .update(payload, 'utf8')
    .digest('hex');

  // Comparación de tiempo constante para evitar timing attacks
  return crypto.timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(`sha256=${expectedSignature}`)
  );
}

// En Next.js App Router
export async function POST(request: Request) {
  const payload = await request.text(); // IMPORTANTE: leer como texto, no JSON
  const signature = request.headers.get('x-webhook-signature') ?? '';

  if (!verifyWebhookSignature(payload, signature, process.env.WEBHOOK_SECRET!)) {
    return new Response('Invalid signature', { status: 401 });
  }

  const event = JSON.parse(payload);
  await processWebhookEvent(event);

  return new Response('OK', { status: 200 });
}
```

La clave técnica es leer el body como texto antes de parsearlo como JSON. La firma se calcula sobre el string exacto que llegó — si parseas a JSON primero y luego vuelves a serializar, el string puede ser diferente (orden de campos, espacios) y la verificación fallará.

## Idempotencia: Procesar Cada Evento Exactamente Una Vez

Los sistemas que envían webhooks pueden reenviar el mismo evento si tu endpoint no respondió con un 200 en el primer intento (timeout, error transitorio, etc.). Tu handler debe ser idempotente: procesar el mismo evento dos veces debe producir el mismo resultado que procesarlo una vez.

```typescript
async function processPaymentConfirmed(event: WebhookEvent) {
  // Verificar si ya procesamos este evento
  const alreadyProcessed = await db.processedWebhooks.findFirst({
    where: { eventId: event.id }
  });

  if (alreadyProcessed) {
    console.log(`Event ${event.id} already processed, skipping`);
    return; // Idempotente: devolver OK sin duplicar la acción
  }

  // Registrar ANTES de procesar (previene race conditions con retry inmediato)
  await db.processedWebhooks.create({
    data: { eventId: event.id, processedAt: new Date() }
  });

  // Ahora procesar el evento
  await db.orders.update({
    where: { id: event.orderId },
    data: { status: 'paid', paidAt: new Date() }
  });

  await sendConfirmationEmail(event.orderId);
}
```

## Procesamiento Asíncrono: Responder Rápido, Procesar Después

El servicio que envía el webhook generalmente espera una respuesta 200 en menos de 5-10 segundos. Si tu handler tiene lógica pesada (enviar emails, actualizar múltiples tablas, llamar a otras APIs), procesar sincrónicamente puede resultar en timeouts y reenvíos innecesarios.

El patrón correcto es: responder 200 inmediatamente, encolar el procesamiento para hacerlo de forma asíncrona.

```typescript
export async function POST(request: Request) {
  // ... verificar firma ...

  const event = JSON.parse(payload);

  // Encolar para procesamiento asíncrono
  await queue.add('process-webhook', event, {
    attempts: 3,
    backoff: { type: 'exponential', delay: 2000 }
  });

  // Responder inmediatamente
  return new Response('OK', { status: 200 });
}
```

Con BullMQ (Redis) o un servicio como AWS SQS, el evento se procesa en background con reintentos automáticos si falla, sin afectar al tiempo de respuesta del endpoint.

## Gestión de Secretos de Webhook

Cada integración de webhook debe tener su propio secreto — no reutilices el mismo secreto para Stripe, GitHub y tu CRM. Si un secreto se compromete, puedes rotarlo para esa integración sin afectar a las demás.

Los secretos de webhook deben almacenarse como variables de entorno y rotarse periódicamente o inmediatamente si hay sospecha de compromiso.
