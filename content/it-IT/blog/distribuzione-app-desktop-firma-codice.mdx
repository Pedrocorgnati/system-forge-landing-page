Hai trascorso mesi a costruire un'app desktop. Il codice è solido, i test passano, la UX è buona. Poi generi l'installer e lo mandi al cliente per testarlo. Lui cerca di aprire il file e riceve: "Windows Defender SmartScreen ha impedito l'avvio di un'applicazione non riconosciuta." O, su macOS: "Non è possibile aprire 'TuaApp.app' perché lo sviluppatore non può essere verificato."

Questo momento è evitabile. Il code signing — firma digitale del codice — è ciò che differenzia un'app che si installa senza allarmi da una che sembra malware per i sistemi operativi moderni. Non è un dettaglio di distribuzione che può essere rimandato. È un requisito per qualsiasi app che verrà installata da utenti reali al di fuori del tuo ambiente di sviluppo.

Il processo è diverso su ogni piattaforma e comporta costi e tempistiche. Capire come funziona prima di arrivare alla fase di distribuzione risparmia settimane di ritardi e brutte sorprese con i clienti.

## Windows: Certificato EV e Authenticode

Windows usa lo standard Authenticode per la verifica del codice firmato. SmartScreen, il sistema di reputazione di Microsoft, analizza due fattori: se il codice è firmato e quale reputazione accumulata ha il certificato usato.

Esistono due tipi di certificati per Windows:

**Certificato OV (Organization Validation):** Verifica che l'organizzazione esista, ma SmartScreen mostrerà ancora un avviso di "editore sconosciuto" nelle prime installazioni finché il certificato non accumula reputazione sufficiente. Per app con pochi utenti, questo può richiedere mesi.

**Certificato EV (Extended Validation):** Richiede verifica di identità in presenza o notarile, costa di più (tipicamente $300-500/anno), ma bypassa immediatamente il processo di accumulo reputazione di SmartScreen. Per app aziendali, l'EV è il percorso corretto.

Fornitori come DigiCert, Sectigo e GlobalSign emettono certificati EV. Il processo di validazione richiede da alcuni giorni a due settimane a seconda del fornitore e della velocità di risposta alla documentazione richiesta.

Con `electron-builder`, la configurazione di signing su Windows è:

```json
{
  "build": {
    "win": {
      "target": ["nsis", "portable"],
      "certificateFile": "cert.pfx",
      "certificatePassword": "${CERTIFICATE_PASSWORD}",
      "signingHashAlgorithms": ["sha256"],
      "signDlls": true
    },
    "nsis": {
      "oneClick": false,
      "allowToChangeInstallationDirectory": true,
      "createDesktopShortcut": true,
      "createStartMenuShortcut": true,
      "shortcutName": "TuaApp"
    }
  }
}
```

`signDlls: true` è importante: senza di esso, viene firmato solo l'eseguibile principale, e le DLL non firmate all'interno dell'installer possono far scattare gli avvisi dell'antivirus.

La password del certificato non deve mai essere nel codice o nel repository. Deve essere una variabile d'ambiente iniettata dal CI/CD — GitHub Actions Secrets, GitLab CI Variables o equivalente.

## macOS: Developer ID e Notarization da Apple

macOS ha un processo in due fasi: signing con un certificato Developer ID, e notarization — invio dell'app firmata per analisi automatizzata da parte di Apple prima della distribuzione.

Il Gatekeeper, il sistema di sicurezza di macOS, dal Catalina (2019) richiede la notarization per qualsiasi app distribuita al di fuori del Mac App Store. Senza notarization, macOS blocca l'apertura dell'app con il messaggio di "sviluppatore non verificato".

Il Developer ID richiede un account nell'Apple Developer Program ($99/anno). Il certificato viene generato tramite Xcode o Keychain Access ed esportato come file `.p12` per l'uso in ambienti CI.

La configurazione in `electron-builder` per macOS:

```json
{
  "build": {
    "mac": {
      "target": ["dmg", "zip"],
      "category": "public.app-category.productivity",
      "identity": "Developer ID Application: La Tua Azienda (TEAM_ID)",
      "hardenedRuntime": true,
      "gatekeeperAssess": false,
      "entitlements": "entitlements.mac.plist",
      "entitlementsInherit": "entitlements.mac.plist",
      "notarize": {
        "teamId": "TEAM_ID"
      }
    }
  }
}
```

`hardenedRuntime: true` è obbligatorio per la notarization. Il file `entitlements.mac.plist` dichiara le autorizzazioni di cui l'app ha bisogno — accesso alla rete, fotocamera, microfono, ecc. Apple analizza se le autorizzazioni dichiarate hanno senso per il tipo di app.

Il processo di notarization richiede da pochi minuti a qualche ora. In una pipeline CI, questo significa che il build di release può richiedere più tempo rispetto ai build di sviluppo. Pianifica questo nel SLA di deploy.

## Linux: AppImage, .deb e Snap

Linux è più permissivo di Windows e macOS in termini di verifica del codice — non esiste un sistema centralizzato equivalente a SmartScreen o Gatekeeper. Ma la scelta del formato di distribuzione impatta direttamente l'esperienza di installazione.

| Formato | Pro | Contro | Indicato per |
|---|---|---|---|
| AppImage | Portabile, senza installazione | Senza auto-update nativo | Distribuzione singola |
| .deb | Integrazione con apt, familiare | Solo Debian/Ubuntu | Ambienti controllati |
| .rpm | Integrazione con dnf/yum | Solo Red Hat/Fedora | Ambienti RHEL aziendali |
| Snap | Distribuzione universale, sandboxed | Avvio più lento | Distribuzione pubblica |
| Flatpak | Sandbox forte, universale | Setup iniziale complesso | App per utente finale |

Per la distribuzione aziendale — dove l'azienda controlla le macchine dei dipendenti — `.deb` o `.rpm` è la scelta più pratica perché permette di automatizzare l'installazione tramite strumenti di gestione della configurazione come Ansible o script di provisioning.

Per la distribuzione pubblica ampia, AppImage ha il vantaggio di funzionare su praticamente qualsiasi distribuzione Linux senza installazione. Snap e Flatpak sono alternative con distribuzione tramite store (Snap Store, Flathub) ma aggiungono complessità al processo di pubblicazione.

## CI/CD per Build Multi-piattaforma

Build per Windows, macOS e Linux in parallelo sono realizzabili con GitHub Actions usando runner specifici per piattaforma:

```yaml
# .github/workflows/release.yml
name: Release Build

on:
  push:
    tags:
      - 'v*'

jobs:
  build:
    strategy:
      matrix:
        os: [windows-latest, macos-latest, ubuntu-latest]

    runs-on: ${{ matrix.os }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm ci

      - name: Build and Sign (Windows)
        if: matrix.os == 'windows-latest'
        env:
          CERTIFICATE_PASSWORD: ${{ secrets.WINDOWS_CERT_PASSWORD }}
          CSC_LINK: ${{ secrets.WINDOWS_CERT_BASE64 }}
        run: npm run build:win

      - name: Build and Notarize (macOS)
        if: matrix.os == 'macos-latest'
        env:
          APPLE_ID: ${{ secrets.APPLE_ID }}
          APPLE_APP_SPECIFIC_PASSWORD: ${{ secrets.APPLE_APP_SPECIFIC_PASSWORD }}
          APPLE_TEAM_ID: ${{ secrets.APPLE_TEAM_ID }}
          CSC_LINK: ${{ secrets.MACOS_CERT_BASE64 }}
          CSC_KEY_PASSWORD: ${{ secrets.MACOS_CERT_PASSWORD }}
        run: npm run build:mac

      - name: Build (Linux)
        if: matrix.os == 'ubuntu-latest'
        run: npm run build:linux

      - name: Upload artifacts
        uses: actions/upload-artifact@v4
        with:
          name: build-${{ matrix.os }}
          path: dist/
```

Il certificato `.p12` è archiviato come base64 in un GitHub Secret (`CSC_LINK`), non come file nel repository. `electron-builder` decodifica automaticamente quando trova il valore in base64.

## Conclusione

Il code signing e la notarization sono investimenti che la maggior parte dei progetti scopre di dover fare fin dall'inizio quando arriva alla prima demo con il cliente e Windows blocca l'installer. Il processo ha costi — tra $100 e $500/anno a seconda delle piattaforme — e tempi di validazione che devono entrare nel cronoprogramma del progetto.

La parte positiva è che, con la configurazione CI/CD corretta, il processo diventa completamente automatizzato dopo il setup iniziale. Ogni release genera installer firmati e notarizzati per tutte le piattaforme in modo trasparente.
